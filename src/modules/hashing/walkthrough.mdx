<Chapter id="sha256">

## SHA-256, one step at a time

A <Term id="hash">hash function</Term> turns any input into a fixed-size fingerprint: 32
bytes for SHA-256. The map above the picture shows the whole trip for `"abc"`: message,
padded block, 64 words, 64 rounds, digest.

<Phase on="sha256.pad" title="Padding">

SHA-256 eats 64-byte **blocks**, so the message is padded: one `0x80` <Term id="byte" />,
zeros, and the message length in bits in the last eight bytes. `"abc"` is 3 bytes, so
its length field says 24.

</Phase>

<Phase on="sha256.block" title="A block becomes sixteen words">

Each block is cut into sixteen **words** of 4 bytes (32 bits) each, W0 to W15. A word
is the unit everything else works on: it is added, rotated and mixed as one number.

</Phase>

<Phase on="sha256.schedule" title="The message schedule">

Sixteen words are stretched to 64. Each new word mixes four earlier ones: two passed
through <Term id="sigma-small" />, two added as they are, so every bit of the block
reaches every later word.

</Phase>

<Phase on="sha256.round" title="64 rounds">

Eight working variables, `a` to `h`, are stirred once per word. Each round computes two
temporaries from <Term id="sigma-big" />, <Term id="ch" /> and <Term id="maj" />, makes a
new `a` and a new `e`, and shifts every other letter one place along. Use the round
slider to jump around.

</Phase>

<Phase on="sha256.add sha256.digest" title="Add, then the digest">

The rounds' result is added back into the running hash value H0–H7, which is what
makes the rounds impossible to run backwards. After the last block, H0–H7 written out
in <Term id="hex" /> is the digest. It matches what every SHA-256 library prints for
`"abc"`: the tests check.

</Phase>

</Chapter>

<Chapter id="avalanche">

## The avalanche effect

Change one bit of the input and about **half** of the 256 output bits change, with no
pattern to which ones.

<Phase on="avalanche.flip" title="Flip one bit">

Here one bit of `"hello"` is flipped, turning `h` (`01101000`) into `i` (`01101001`). The
inputs differ by a single square.

</Phase>

<Phase on="avalanche.hashA avalanche.hashB" title="Hash both">

Both messages go through the same SHA-256. The two digests share nothing you could
spot: the closeness of the inputs doesn't survive.

</Phase>

<Phase on="avalanche.diff" title="Compare">

The highlighted hex characters differ, and each filled square below is an output bit
that flipped. It won't be exactly 128: like tossing 256 coins, it lands near half, give
or take a dozen. In Free play, pick any message and any bit.

</Phase>

</Chapter>

<Chapter id="hmac">

## From a hash to a MAC

A <Term id="mac" /> proves a message came from someone who knows a secret key and
wasn't changed on the way.

<Phase on="hmac.naive" title="Why not SHA-256(key ‖ message)?">

SHA-256's digest is its whole internal state, so anyone holding that tag can carry on
hashing and get a valid tag for a longer message. That is a **length-extension
attack**.

</Phase>

<Phase on="hmac.key" title="One block of key">

**HMAC** first makes the key exactly one 64-byte block, K0: padded with zeros, or hashed
first if it is longer.

</Phase>

<Phase on="hmac.ipad hmac.inner" title="Inner lane">

K0 is <Term id="xor">XORed</Term> with `0x36` (ipad) and the message is hashed after
it. Expand the hash to see its SHA-256 blocks.

</Phase>

<Phase on="hmac.opad hmac.outer" title="Outer lane">

K0 is XORed with `0x5c` (opad), and the inner hash travels across to be hashed after
it. The outer hash's input is short and fixed.

</Phase>

<Phase on="hmac.tag" title="The tag">

The outer hash is the tag. Extending it only extends the outer hash's input, and
nobody can compute a new inner hash without the key.

</Phase>

</Chapter>
