<Chapter id="lookup">

## Unsalted hashes leak

<Phase id="unsalted-storage">

A server should never store your password. It stores its <Term id="hash" /> instead, and
at login hashes what was typed and compares. But alice and carol chose the same password,
so they have the **same hash**: anyone reading the table sees it without cracking anything.

</Phase>

<Phase id="unsalted-lookup">

People choose the same few passwords. An attacker hashes the 200 most common ones **once,
in advance**, then looks each stolen hash up instantly. Four of the five users fall. (A
real _rainbow table_ stores chains of hashes to save space, but answers the same question.)

</Phase>

</Chapter>

<Chapter id="salt">

## Salts defeat precomputation

<Phase id="salted-storage">

The fix is a <Term id="salt" />: random bytes, different for every user, stored next to
the hash as `salt ‖ SHA-256(salt ‖ password)`. The salt isn't secret. It only makes every
user's input different, so alice's and carol's hashes now differ.

</Phase>

<Phase id="salted-lookup">

The attacker's table was built without these salts, so it matches nothing. A table per
salt is no faster than plain guessing. But one user can still be attacked directly, and
SHA-256 is fast: billions of guesses a second on one graphics card.

</Phase>

</Chapter>

<Chapter id="pbkdf2">

## Slow hashing with PBKDF2

<Phase id="pbkdf2-setup">

If guesses are cheap, make each one **expensive**. PBKDF2 repeats <Term id="mac">HMAC</Term>
many times. OWASP recommends **600,000** iterations: the server pays that once per login,
an attacker pays it for every guess.

</Phase>

<Phase id="pbkdf2-block-1">

`U1 = HMAC(password, salt ‖ block number)`, then `U2 = HMAC(password, U1)`, and so on,
with every `U` folded into the result by <Term id="xor" />. Step through three, then run
all 600,000 for real in a background thread, which you can cancel.

</Phase>

<Phase id="pbkdf2-key">

Each block of 32 bytes is one such chain; the derived key is the blocks joined and cut to
length.

</Phase>

</Chapter>

<Chapter id="cost">

## What each guess costs

These bars estimate how long one attacker needs to try every password in a set. They use
a log scale: each step along the axis is ten times longer. Add graphics cards or raise the
work factors and watch them move.

**bcrypt** (1999) repeats the Blowfish cipher's slow key setup `2^cost` times. **Argon2id**
(RFC 9106, 2021) also needs a large block of **memory** per guess, which takes away most
of a graphics card's advantage.

bcrypt and Argon2 are described here, not computed. The speeds are illustrative orders of
magnitude from one public benchmark, and each shows its source.

</Chapter>
